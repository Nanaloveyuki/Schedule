# Android 提醒、后台任务与日历集成

## 项目背景

这个课程表项目的提醒功能不是简单 UI 开关，而是后续真正要落到系统能力上的功能点，因此需要尽早明确策略边界。

## 产品策略

当前已经确定的提醒方向是双通道：

- `应用内通知`
- `系统日历事件`

其中系统日历事件属于可选能力，应在用户授权日历权限后再启用，不应强绑为唯一方案。

## Android 官方资料摘要

### 后台任务概览

Android 官方后台任务概览页面强调：

- 后台 API 的选择取决于任务是否可延迟、是否必须精确、是否由用户触发、是否需要在系统限制下持续执行
- 不同场景应分别选择 `WorkManager`、前台服务、其他系统调度能力

对本项目的直接含义：

- 普通提醒调度优先考虑 `WorkManager`
- 对时间精度要求更高的场景再考虑 `AlarmManager`
- 不要默认上前台服务

### 日历提供程序

Android 官方日历提供程序文档说明：

- 系统日历通过 Calendar Provider 暴露数据
- 应用可以在获得权限后读写日历与事件
- 这种能力适合“把应用任务同步到系统日历”场景

对本项目的直接含义：

- “定时任务写入系统日历事件”是合理方案
- 但它不是通知的完全替代品，因为用户可能并不希望污染系统日历

## 本项目建议的能力分层

### 第一层：领域模型

先在 `domain` 层表达提醒方式，而不是直接写死平台实现。

当前项目已这样做：

- `ReminderChannel.InAppNotification`
- `ReminderChannel.SystemCalendar`

这样做的好处：

- 页面和配置先稳定
- 平台实现可以后补

### 第二层：本地配置

当前已经支持在 UI 中保存提醒任务，并选择提醒方式。

这一步先保证：

- 配置能保存
- 配置能展示
- 配置结构不依赖最终平台能力是否已经全部完成

### 第三层：平台实现

后续再补：

- 应用内通知渠道创建
- 通知权限申请
- 定时调度
- 日历权限申请
- Calendar Provider 插入事件

## 适合本项目的实现顺序

1. 先做应用内通知。
2. 再做普通提醒的调度。
3. 最后补系统日历事件写入。

原因：

- 应用内通知更符合“课程提醒”主需求
- 日历写入属于可选增强能力
- 系统日历通常还需要处理重复事件、删除同步、用户已有日历选择等细节

## 风险点

### 1. 厂商后台限制

仅靠模拟器无法验证真实提醒到达率。

后续提醒能力落地时必须上真机测试，尤其是：

- 熄屏
- 省电模式
- 应用被系统回收

### 2. 精确定时不要默认开启

“精确定时”会带来更高的系统限制与实现复杂度，建议把它保留为可选项，而不是默认路径。

### 3. 日历不是通知的替身

系统日历事件更像一种同步与可见性增强方案，不等于“通知一定可靠”。

## 当前结论

- 产品上同时支持应用内通知与系统日历事件是合理的。
- 技术上先做通知，再做日历，是更稳的推进顺序。
- 架构上继续把提醒方式留在 `domain` 层抽象，不把平台逻辑提前揉进界面和 ViewModel。
